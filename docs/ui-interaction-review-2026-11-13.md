## P1：建议优先修复

### 1. 等待状态只禁用一个按钮，无法阻止同一表单再次提交

位置：`app/static/app.js:4`；`app/templates/settings.html:85`。

复现：在通知表单点击“发送测试消息”，请求未完成时点击“保存通知设置”。

实测：测试按钮变为“发送中…”并禁用，保存按钮仍可点击。原生浏览器请求记录同时出现 `/settings/test_tg` 和 `/settings/notify` 两个 POST。再次通过 `requestSubmit()` 触发提交时，脚本遇到已禁用按钮直接返回，没有调用 `preventDefault()`，也没有检查表单是否已经忙碌。

影响：同一份配置可以在前一个动作未结束时再次写入，后一个导航会覆盖前一个结果反馈；网络取消也不保证前一个服务器动作未执行。30 秒定时重新启用按钮同样没有确认请求是否结束。

建议：在表单层维护提交状态；忙碌时阻止后续提交；统一禁用该表单所有提交入口，并正确处理导航失败和浏览器历史恢复。提交目标需要在锁定按钮时保留。

证据：`artifacts/ui-interaction-review-2026-11-13/native-submission-results.json`。

### 2. 缺少通知凭据仍显示“已启用”和“保存成功”

位置：`app/main.py:1081`；`app/templates/settings.html:19`；`app/monitor.py:319`。

复现：在没有已保存 Token 的情况下，勾选“启用 Telegram 通知”，将 Token 和 Chat ID 留空后保存。

实测：返回保存成功，开关和徽标显示“已启用”；数据库保存 `tg_enabled=1`，后台 `_deliverable('change')` 却返回 `False`，实际不能发送通知。

影响：用户容易把“启用开关”理解为通知已经具备发送条件，故障时收不到提醒。

建议：启用时对有效 Token 和 Chat ID 做条件必填校验；允许保存草稿时，应明确显示“配置不完整”，并区分“已启用”和“测试通过”。

证据：`browser-results.json` 的 `notify_enable_with_missing_credentials`，以及 `backend-results.json`；以下证据文件均在同一审查产物目录。

### 3. 清除 Token 后，测试仍可能使用没有保存的新 Token 成功发送

位置：`app/main.py:1092`、`app/main.py:1137`；`app/templates/settings.html:40`。

复现：已有 Token 时，勾选“清除已保存的 Token”，同时填写新 Token，再点击“发送测试消息”。

实测：保存逻辑按提示清空 Token，测试逻辑却重新读取表单里的新 Token。模拟发送收到新 Token，页面提示“测试消息已发送”，数据库中的 Token 仍为空。

影响：测试结果与最终保存的运行配置不一致；用户可能误以为通知配置可用。

建议：保存和测试共用一次解析后的有效配置，例如使用 `_save_notify()` 返回的 `vals`；清除后有效 Token 为空时，测试应就近报错。

证据：`backend-results.json` 的 `clear_token_plus_new_token_test_succeeds_with_unsaved_token`。

### 4. 无效 DNS 服务器被静默替换，仍提示操作成功

位置：`app/main.py:639`、`app/main.py:823`、`app/main.py:937`；`app/templates/new.html:58`。

复现：添加监控项时将 DNS 服务器填为 `1.1.1.999`，其余输入有效后提交。

实测：浏览器未拦截，后端将其替换成 `223.5.5.5`，页面仅提示添加成功。更新页面同样会静默沿用旧值。

影响：用户以为正在使用自己指定的解析器，实际检查结果来自另一台服务器，可能直接影响监控判断。

建议：无效 IPv4/IPv6 应返回字段错误并保留原始输入；仅对明确允许为空的情况使用默认值。

证据：`browser-results.json` 的 `invalid_resolver_silently_falls_back`；截图 `invalid-resolver-success.png`。

### 5. 记录类型冲突后，整个编辑草稿丢失

位置：`app/main.py:941`、`app/main.py:949`；`app/templates/domain.html:211`。

复现：同一域名已经同时有 A/AAAA 监控项；在 A 项编辑备注、间隔并切换为 AAAA，然后保存。

实测：提示类型冲突后重定向到原详情，备注、间隔、记录类型全部恢复数据库旧值；没有字段级 `aria-invalid`，页面也未定位到监控设置。

影响：一次可恢复的字段冲突导致其他正确输入一并丢失，用户需要重填。

建议：参照添加页面的错误处理，直接重新渲染编辑页，保留非敏感草稿，给记录类型标记错误并定位错误摘要或字段。

证据：`browser-results.json` 的 `conflict_discards_domain_draft`；截图 `conflict-draft-lost.png`。

### 6. 时间线点击/触摸显示第一段，未选择实际点击的段

位置：`app/static/timeline.js:7`；`app/templates/domain.html:98`。

复现：在详情页 90 天时间线的靠右位置点击或触摸一个色块。

实测：脚本只监听 focus 和 keydown；点击使轨道获得焦点后，`show(0)` 展示第一段。触屏点中段的 IP 为 `203.0.113.42`，实际提示却为第一段的 `198.51.100.23`。鼠标悬浮只可能取得原生 title，不会同步上方详情。

影响：用户看到的 IP、日期和时长与手指选择的位置不对应。键盘方向键和展开文本明细可作为绕行路径，但不能修正触摸选择行为。

建议：为色块添加统一指针/触摸选择处理，按实际目标更新当前索引和详情，同时保留方向键支持；点击 marker 或空白区域时应定义明确行为。

证据：`followup-results.json` 的 `mobile_timeline_screenshot`；截图 `mobile-timeline-wrong-segment.png`。

## 已验证正常的行为

- 登录必填校验在提交前生效，按钮不会因此错误进入等待状态。
- 添加域名失败会保留域名、备注、检查间隔，并关联域名错误文案。
- 成功提示刷新后不重复显示；手动检查结果返回详情页。
- 删除按钮默认折叠，展开后才可确认；同时说明对象、删除范围与不可恢复性。
- 移动菜单支持 Esc 关闭并将焦点还给菜单入口，点击菜单外区域可关闭。
- 图表和时间线支持键盘方向键与可见焦点，均有文本数据替代入口。
- 所有审查视口下无页面横向溢出，明暗主题的现有结构、对比度和视觉门禁通过。
